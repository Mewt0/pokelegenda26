## Подтверждённый исходный срез

| Объект | Факт |
|---|---|
| Локации | 155 в build; 123 ключа в config/location_content.php |
| Расхождения карты | 42 DB-локации без записи в конфиге; 10 ключей конфига без DB-локации |
| NPC | 80 конфигурационных записей; 36 legacy PHP-файлов — не взаимно однозначные сущности |
| Новые определения квестов | 14 определений, 40 шагов |
| Существующий прогресс | 3339 строк в quest |
| Неопределённый в новом слое квест | ID 666, 59 строк прогресса |
| Квестовые спавны | Проверяемые 13 видов покрыты существующими спавнами |

Количество записей не доказывает функциональный паритет. Отсутствие конфигурации не означает сломанную локацию: возможны DB-fallback, транспортные и служебные экраны. Среди 42 записей — ярмарка, существующие регионы Hoenn/Sinnoh/Unova и самолёт. Сначала классификация, потом исправления.

Legacy npc_16.php связывает квест 666 с «Пророком» и событийной цепочкой. Требуется проверка актуальности события, наград, боёв и каждого сохранённого этапа. Не включать событие автоматически и не удалять его прогресс.

`tools/regions_connectivity.php` симметризует переходы для анализа: его достижимость не доказывает доступность направленного маршрута с условиями. Односторонний переход не исправлять автоматически.

## Очередь реализации

1. Зафиксировать реестр NPC/цепочек: старый источник → новый обработчик, условия, предметы, бои, награды, cooldown, сохранённый прогресс, доказательство проверки. Статусы «обнаружено», «перенесено», «проверено», «опубликовано» различать.
2. Выдача предметов v2: поиск получателя → понятный конструктор → серверный preview → подтверждение с причиной → квитанция. Идемпотентность и атомарные начисление/квитанция/audit обязательны. Флаг изначально выключен.
3. Выдача покемонов по тому же сценарию; базовые поля сразу, IV/EV и ручные статы в дополнительных настройках. Согласовать UI с серверным пределом IV 31; сохранять текущий транзакционный расчёт и выдачу атак.
4. Единая история игрока/объекта/операции поверх существующих журналов: фильтры, correlation ID, пагинация, маскирование секретов. Не создавать параллельную бессвязную систему логов.
5. Трекеры ошибок, доставки наград и прохождения квестов: этапы, зависания, повторные получения; без сбора приватной переписки. Уточнить доступы и срок хранения.
6. Перенос NPC/квестов небольшими цепочками с сохранением ID/прогресса. Мастер сейчас создаёт черновики NPC/квестов, не публикует их. Публикацию вводить отдельно с валидацией и флагом.
7. Разобрать 42/10 расхождений карты, затем проверить направленные маршруты, условия входа и возвращения. Новые локации добавлять только для подтверждённой потребности контента; 13 проверенных видов покемонов новых локаций не требуют.

## Уточнения к предложению Harness

- Предлагаемые таблицы, токены preview, флаги и API ещё не реализованы; перед схемой проверить существующие ledger/reward-механизмы и избегать дублирования.
- Конкретные HTTP-коды отказов согласовать с текущим API, а не принимать предложенный 419 как уже существующий контракт.
- После rollback начисления failed-attempt можно сохранить отдельной безопасной записью; нельзя одновременно откатить транзакцию и обещать сохранение строки внутри неё.
- Прогресс сверять не только с user_quest_tracking: основной обнаруженный массив — quest (3339 строк). Не выполнять двойное начисление при dual-read.
- Повтор ключа с другим payload должен отклоняться; повтор того же запроса возвращает прежнюю квитанцию. Компенсации не удаляют историю и не забирают автоматически уже переданные/использованные объекты.
