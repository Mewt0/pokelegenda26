# Задание для внешнего исполнителя: реализовать 130 особых атак

Файл со списком и группами: **`docs/design/SPECIAL_ATTACKS_SPEC.md`** (130 атак, 25 групп).
Полный перечень с разбивкой «работает / не работает»: `docs/design/SPECIAL_ATTACKS_AUDIT.md`.

## В чём проблема

В игре **186 атак** имеют в данных побочный эффект (данные из `attac_dop` — 133 строки,
и `stat_attak` — 55 строк). Реализовано в бою **56**, не реализовано **130**.

Игрок использует, например, `Bite`, `Ember`, `Ice Punch`, `Body Slide`, ждёт дополнительного
эффекта — а его нет: атака наносит только базовый урон и молча ничего больше не делает.

## Почему так вышло (важно для исполнителя)

Движок реализует особые эффекты **по названию атаки**, а не по номерам эффектов из таблиц.
В `src/Game/BattleMoveEffectCatalog.php` есть функция, которая нормализует название
(нижний регистр, всё не-буквенное → пробел) и матчит по строкам:

```php
'spikes' => 'spikes',
'toxic spikes' => 'toxic_spikes',
'stealth rock', 'stone axe' => 'stealth_rock',
'sticky web' => 'sticky_web',
'ceaseless edge' => 'spikes',
```

То есть поддержаны только те атаки, которые кто-то вписал руками. Колонки эффектов в
`attac_dop` (`dop_effc`, `tip_s`, `setting`) движком **не читаются** — проверено поиском по коду.

## Где что лежит

| Что | Где |
|---|---|
| Движок боя | `src/Game/BattleEngineService.php` (170 КБ) |
| Каталог эффектов (куда добавлять) | `src/Game/BattleMoveEffectCatalog.php` |
| Таблица атак | `attac_power` — 937 строк: `atac_id`, `atac_name`, `atac_power`, `atac_pp`, `atac_accuracy`, `atac_not`, `dop_effect`, `stati`, `chans_effect`, `critic`, **`priorety`** |
| Побочные эффекты | `attac_dop` — `id_attc`, `dop_effc`, `setting`, `tip_s`, `def/atc/sdef/satc/speed/acc/accuracy` |
| Изменение статов | `stat_attak` — `id_atk`, `tip`, `tip_b`, те же статы |

## Порядок работы

1. Взять группу из спецификации (они отсортированы по количеству атак: 23, 21, 11, 10, 9, 8 …).
2. Для каждой атаки группы добавить обработку по имени в `BattleMoveEffectCatalog`, а если эффект
   влияет на ход боя — и в `BattleEngineService`, по образцу уже работающих `spikes`, `stealth rock`.
3. **Сверить смысл эффекта с данными**, а не догадываться: в спецификации у каждой группы указаны
   `dop_effc`, знак (`tip_s`), изменяемые статы и номер статуса. У 56 уже работающих атак те же
   поля — по ним можно понять соответствие «номер эффекта → поведение».
4. Проверять после каждой группы: `php -l` по изменённым файлам и гейт
   `php tools/open_test_regression.php --profile=quick --login=Tacos --password=REDACTED_USE_SMOKE_PASSWORD`
   (ожидание `Passed: 25, failed: 0, skipped: 0`), плюс живой PvE-бой хотя бы одной атакой из группы.

## Ловушки проекта, на которых уже падали

- **PDO с `EMULATE_PREPARES=false`: один именованный параметр нельзя использовать дважды** в одном
  запросе. Для повторного значения заводится отдельное имя (в проекте так сделано: `:now` и `:now_end`).
- Не менять внешний вид и порядок существующих эффектов: 56 атак уже работают, их поведение менять нельзя.
- Не добавлять эффект «на глаз»: если по данным непонятно, что делает атака, — вынести её в список
  «требует уточнения», а не реализовывать наугад.

## Что нужно уточнить по данным (честное ограничение)

Группы в спецификации построены **механически** по значениям колонок. Смысл конкретных номеров
(`dop_effc = 5/6`, `setting = 1`, а также значения `1` в колонках статов) в коде не задокументирован.
Надёжный способ выяснить соответствие — сравнить поля у 56 **уже работающих** атак с их поведением
в боевом коде. Это первый шаг работы, до реализации новых.

## Ожидаемый результат

- список 130 атак сокращён до нуля нереализованных (или явно помечены те, что реализовать нельзя);
- каталог эффектов дополнен по именам, движок учитывает новые эффекты в бою;
- гейт зелёный, миграций не требуется (данные уже есть, правится код);
- отчёт: какие группы закрыты, чем проверено, что осталось спорным.
