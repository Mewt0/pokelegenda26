# TASK-033 — P1: `http_smoke` оставляет открытый PvE-бой и лок `users.pve`

**Исполнитель:** Codex-агент · **Зона:** `tools/http_smoke.php` (и, если причина там, соответствующий вызов API) · **Статус:** todo

## Проблема (измерено DSH-агентом 2026-10-09)

`tools/http_smoke.php` после каждого прогона оставляет `Tacos` в бою:

```
до:    {"pve":0,"pvp":0,"trade":0,"battleid":0}
после: {"pve":1,"pvp":0,"trade":0,"battleid":1791515393}
battles: {"id":1791515393,"user_1":1,"batl_tip":"pve","pobeda":0,"raund":1,"times":1791518993}
```

При этом после **полного** `tools/open_test_regression.php --profile=quick` состояние чистое — то есть утечка возникает именно на шаге `http_smoke` внутри прогона и переживает его.

## Последствия

1. **Гейт `quick` красный.** `http_smoke` выполняется раньше `commission_hardening_smoke`; тот видит `users.pve=1` и падает на `expire.create` («Сначала закончите бой или обмен»), потому что `CommissionMarketRepository::userBusy()` (`src/Repository/CommissionMarketRepository.php:1168`) читает `pve`. Итог: `quick` = 23/24 вместо 24/24, и это **не** связано с накопленными старыми боями.
2. **Прогоны загрязняют боевые данные.** За сессию 2026-10-09 число незавершённых PvE-боёв выросло 211 → 214, а пользователей с `pve=1` — примерно 130 → 132: каждый прогон регрессии добавляет одну зависшую запись.
3. **`TASK-032` (реапер) этого не лечит и не должен:** бой свежий, `times` в будущем, корректный реапер его не тронет.

## Что сделать

1. Найти в `tools/http_smoke.php` (или в вызываемом им API-эндпоинте) шаг, который начинает PvE-бой и не завершает его.
2. Привести прогон к чистому состоянию: либо завершать бой тем же публичным API, либо не создавать его в read-only режиме, либо оборачивать создание в транзакцию с откатом (как это уже сделано в `tools/pve_stale_battle_reaper_smoke.php`).
3. Если причина в самом API (например, старт боя не имеет симметричного завершения для read-only проверки) — **не править API** (`src/**` вне зоны этой задачи), а описать в отчёте и предложить отдельную задачу.
4. Добавить в смоук проверку, что после прогона `users.pve/pvp/trade = 0` и `battleid = 0` — чтобы утечка больше не появлялась незаметно.

## Границы

`tools/**`. Нельзя: трогать `src/**`, `views/**`, `public/**`, `public/css/**`, `public/js/**`; мутировать боевую БД иначе как через штатные вызовы API; менять набор и смысл существующих проверок смоука.

## Критерии приёмки

1. `php -l` на изменённые файлы — чисто.
2. До прогона `Tacos` не в бою; после `php tools/http_smoke.php --login=Tacos --password=...` — **тоже не в бою**: `SELECT pve,pvp,trade,battleid FROM users WHERE login='Tacos'` → `0,0,0,0`, и по `battleid` нет строки с `pobeda=0`.
3. `Result: 52 checks, 0 failures` сохраняется.
4. `php tools/open_test_regression.php --profile=quick --login=Tacos --password=...` → **24/24** (сейчас 23/24 именно из-за этой утечки).
5. Число незавершённых PvE-боёв до и после прогона **не растёт**.
