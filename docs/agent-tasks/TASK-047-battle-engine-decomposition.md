# TASK-047 — Распил `attackLocked` и `BattleEngineService` на сервисы

**Исполнитель:** Codex-агент (`gpt-5.5`, `model_reasoning_effort=low`) · **Приоритет:** P1
**Зона (явно разрешена):** `src/Game/BattleEngineService.php` и **новые** файлы в `src/Game/`
**Запрещено:** менять `src/Repository/**`, `public/**`, `views/**`, SQL и формат ответов API

---

## Причина

`src/Game/BattleEngineService.php` — 3 217 строк. Крупнейший метод — `attackLocked`,
строки **287–546** (~260 строк): изоляция хода, выбор атак, порядок хода, запись лога,
начисление награды, падение врага, падение игрока, ветки боссов, запись replay и
формирование ответа живут в одном теле.

В этом же методе жили два реальных дефекта, которые уже латались точечно: «двойной клик
начислил награду дважды» и «зависший бой». Пока метод такой, следующая такая дыра
появится снова, потому что ни одну ветку нельзя ни проверить отдельно, ни увидеть
глазами в диффе.

## Что замерено сейчас

| Метод | Строки |
|---|---|
| `attackLocked` | 287–546 (~260) |
| `applyMove` | 1660 |
| `damageMove` | 2174 |
| `applyStartOfTurnStatus` | 2392 |

В `BattleEngineService.php` нет прямых обращений к `$this->db->prepare/query/exec`
(проверено grep'ом по `src/Game`), поэтому задача **не пересекается** с `TASK-052`.

## Что сделать

1. Разбить `attackLocked` на последовательность шагов; после распила тело метода должно
   читаться как список шагов и быть **не длиннее 60 строк**. Предлагаемая нарезка
   (уточняй по коду, не ломая поведение):
   * изоляция хода — уже вынесена (`releasePveBattleActionLock`), не трогать;
   * подготовка боя: загрузка бойцов, fallback, статусы, погода входа, запись действия
     в replay;
   * выбор атак и расход PP;
   * порядок хода и применение атак (`applyMove`);
   * разрешение падения врага, включая ветку продолжения боссового боя;
   * выдача награды (монеты, опыт, EV, счастье, дропы, значок, уведомление, quest-хук,
     запись rollback в safe storage);
   * разрешение падения игрока и ветки боссов;
   * сборка ответа (финальный и промежуточный).
2. Вынести расчёт урона (`damageMove`, 2174) и применение статусов
   (`applyStartOfTurnStatus`, 2392) в отдельные сервисы с явными входами и выходами.
3. `BattleEngineService` остаётся **фасадом**: публичные методы (`attack`, `state`,
   `pvpState` и остальные) сохраняют имена, сигнатуры и форму ответа. Новые сервисы
   получают зависимости через существующую сборку сервисов — найди её в коде и
   используй как есть; **новый DI-контейнер не изобретать**.
   Проверенный факт: DI-контейнера в проекте нет, зависимости собираются вручную в
   `public/index.php:107-191`, и `tools/*.php` тоже конструируют сервисы сами. Этот файл
   **вне твоей зоны**, поэтому новые сервисы создаются либо внутри
   `BattleEngineService` (если они без состояния), либо принимаются необязательным
   параметром конструктора с рабочим значением по умолчанию — так, чтобы существующие
   вызовы не пришлось менять.
4. Новые классы — в `src/Game/`, namespace копируй из первой строки
   `BattleEngineService.php` (`src.zip`-подобных ручных `require` не добавлять, если их
   нет в проекте; автозагрузка уже покрывает `src/`).
5. Ориентир по размеру: каждый новый сервис 300–500 строк, ни один файл после распила —
   больше 1 200 строк.

## Главное ограничение: это перенос, а не переписывание

* Тела методов переносятся **дословно**. Если строка всё же меняется — это отдельный
  пункт в отчёте с объяснением, зачем.
* Никаких новых условий, новых наград, «попутных исправлений» и переименований полей
  ответа. Любая правка поведения — это отдельная задача.
* Ничего не удалять из класса, пока не доказано, что метод не вызывается
  (`grep` по `src/**` и `public/**`; список проверенных вызовов — в отчёт).
* Не коммитить, не пушить, не откатывать чужие изменения в рабочей копии.
