## Причина

`public/js/game-start-runtime.js` собирает HTML вручную строками и вставляет его через `innerHTML`. Из этого выросли четыре разных дефекта, а не один:

* найденный **DOM-XSS** — исправлен в `public/js/game-start-runtime.js:2222`;
* **мерцание спрайта** (TASK-042) — перерисовка полного блока строкой заново инициализировала GIF;
* **перекрывающиеся тосты** — накопление узлов, которыми никто не управляет как объектами;
* **уезжающая нижняя панель** — перезапись контейнера целиком вместо точечного обновления.

Пока рендер идёт строками, каждый новый экран повторяет ту же ошибку: данных в разметке не отследить, а любой пользовательский текст потенциально становится разметкой.

## Что замерено сейчас

* `public/js/game-start-runtime.js` — **2 541** строка.
* Крупнейшие функции: `renderNpcDialog` ~**302** строки, `renderInventoryTargetControls` ~**220**, `renderBattle` ~**150**.
* Контракт, который обязан сохраниться при любом распиле (проверено по коду, не по документации):
  * `window.state` и `window.PokemonGameState` — один и тот же объект с полем `locationId`; читается извне в `public/js/chat.js:72-76`;
  * `window.PokemonBattle.loadState` и `window.PokemonBattle.loadBattleState` — выставляются в `game-start-runtime.js:1975-1977`;
  * событие `pokemon:location-changed` — диспатчится в `game-start-runtime.js:569`, слушается в `public/js/chat.js:64`;
  * событие `pokemon:quest-guide` — диспатчится в `public/js/quest-journal.js:374`, слушается в `game-start-runtime.js:2589`;
  * конфиг приходит JSON-блоком `#gameRuntimeConfig` (`views/game-start.php:483-485`), скрипт подключается тегом в `views/game-start.php:488`;
  * инициализация в конце файла: `loadState()`, `fetchGameNotifications()` и три `setInterval` (`game-start-runtime.js:2747-2755`).
* Сборщика в проекте нет: подключение — обычные `<script src>` в фиксированном порядке (`views/game-start.php:486-497`). `chat.js` читает глобальные объекты рантайма, то есть порядок и синхронность подключения — часть контракта.

## Что сделать

1. **Правило для всех новых правок, вводится немедленно и действует с этого момента:** разметка строится только через `document.createElement`, `<template>` + `cloneNode`, `textContent`, `setAttribute`, `classList`, `append`. Подстановка пользовательских данных (ник, название покемона, текст NPC, сообщение чата, имя предмета) в HTML-строку и в `innerHTML` запрещена. `innerHTML` допустим только для статического литерала без единой подстановки, и это должно быть видно по коду.
2. **Распустить файл по экранам** с сохранением точек входа и контракта выше: бой, инвентарь, NPC, карта. Отдельные файлы подключаются теми же `<script src>` в `views/game-start.php` в правильном порядке; `type="module"` не вводить — переход на модули меняет момент выполнения и ломает синхронный контракт с `chat.js` (нужно отдельное решение владельца).
3. **Делать пошагово, по одному экрану за раз**, каждый шаг — самостоятельная проверка. Предлагаемый порядок (можно менять, но обосновать):
   * шаг 0 — зафиксировать контракт: перечислить в отчёте все глобальные точки входа, события и DOM-id, на которые смотрят другие файлы (`chat.js`, `quest-journal.js`, `trainer-profile-window.js`, `player-menu.js`, `game-market-overlay.js`, `mail-overlay.js`, `commission-market.js`), и подтвердить поиском, что список полон;
   * шаг 1 — бой (`renderBattle`, ~150 строк);
   * шаг 2 — инвентарь (`renderInventoryTargetControls`, ~220 строк);
   * шаг 3 — NPC (`renderNpcDialog`, ~302 строки);
   * шаг 4 — карта.
   После каждого шага — полный набор проверок из «Приёмки», а не только `node --check`.
4. Правило из пункта 1 применить и к строкам, которые уже есть в переносимом коде: если при переносе экрана обнаруживается подстановка в HTML-строку — перевести её на DOM-узлы в этом же шаге и указать в отчёте, где именно.
5. Попутные дефекты (мерцание спрайта, наложение тостов, уезжающая панель) чинить только там, где они прямо вызваны склейкой строк и в пределах переносимого экрана. Дизайн-рефреш «заодно» не делать.
