# TASK-037 — PDO: один именованный параметр дважды в запросе даёт HY093

**Исполнитель:** Codex-агент · **Зона (явно разрешена):** `src/Game/NpcDialogEventTrait.php`
**Приоритет:** P1 — латентные падения на живых путях ипподрома

---

## Причина, уже доказанная трижды

Подключение идёт с `PDO::ATTR_EMULATE_PREPARES => false` (см. `src/Database/Connection.php`).
При выключенной эмуляции PDO **не может подставить одно значение в два места** одного
запроса и бросает `SQLSTATE[HY093]: Invalid parameter number`.

Этот дефект уже дважды ломал проект в этой сессии:

1. `src/Game/StalePveBattleReaper.php` — параметр `:pvp_user` дважды. Из-за этого
   применение реапера **падало на каждой попытке** снять лок, а смоук этого не видел,
   потому что проверял свою копию SQL (разобрано в `TASK-034`).
2. `src/Repository/InventoryRepository.php` — параметр `:take` дважды. Уронило гейт
   с 24/24 до 19/24: падала вся экономика (разобрано в `TASK-012`).

## Что найдено сейчас

DSH-агент прогнал сплошной аудит по `src/**` и нашёл **три оставшихся случая** в
`src/Game/NpcDialogEventTrait.php`. Гейт их не ловит — он не покрывает ипподром,
то есть это латентные падения, а не теория.

Строка 320–331:

```php
'UPDATE hippodrome_participants
    SET status = :status, place_num = :place, prize_amount = :prize,
        reward_claimed_at = IF(:prize > 0, :now, reward_claimed_at), updated_at = :now
  WHERE id = :id LIMIT 1'
->execute(['status' => ..., 'place' => ..., 'prize' => $prize, 'now' => $now, 'id' => ...]);
```

`:prize` — два вхождения, одно значение. `:now` — два вхождения, одно значение.

Строка 338–339:

```php
'UPDATE hippodrome_races SET status = "finished", settled_at = :now, updated_at = :now WHERE id = :id LIMIT 1'
->execute(['now' => $now, 'id' => ...]);
```

Строка 356–357:

```php
'UPDATE hippodrome_races SET status = "cancelled", settled_at = :now, updated_at = :now, note = :note WHERE id = :id LIMIT 1'
->execute(['now' => $now, 'note' => ..., 'id' => ...]);
```

## Что сделать

1. Исправить все три места: развести параметры по числу вхождений (`:prize_value` /
   `:prize_check`, `:now_settled` / `:now_updated`) и привязать каждый. Не полагайся на
   передачу одного значения дважды — это тоже неверно при выключенной эмуляции.
2. **Прогнать аудит по всему `src/**` самому** и убедиться, что не осталось ни одного
   запроса с дублированным именованным параметром. Аудит, которым пользовался DSH-агент:
   для каждого файла взять все строковые литералы внутри `prepare(`, вытащить из них
   все `:имя`, сгруппировать и проверить, что нет группы с count > 1. Приведи в отчёте
   итоговое число найденных и исправленных.
3. Отдельно ответь: почему этот паттерн возникает снова и снова, и что стоило бы
   добавить, чтобы он не повторялся (например проверка в `tools/**` — предложи, но в
   этой задаче не реализуй, `tools/**` вне зоны).
