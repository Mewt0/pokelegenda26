**Исполнитель:** Codex-агент (`gpt-5.5`, `model_reasoning_effort=low`) · **Приоритет:** P1
**Зона (явно разрешена):** `tools/**`, `database/migrations/**` (новый файл миграции), `docs/**`
**Запрещено:** применять миграцию к живой БД, удалять или «чистить» строки данных, коммитить

**Статус задачи заранее известен: доводится до `blocked` с вопросом владельцу.** Это

## Причина

В 86 файлах миграций проекта **ноль** вхождений `FOREIGN KEY` (проверено grep'ом).
Целостность держится только кодом, и это уже видно в живых данных.

Любая правка инвентаря, разведения, комиссионки или наград может потерять или задвоить
объект игрока, и база это не остановит: дефект с `:pvp_user` уже ломал реапер, а catch
попадал в чужую PvP-строку через дубль `battles.id`.

Живой `php tools/db_integrity_smoke.php --json` (2026-10-11): `P0=0`, `P1=0`, при этом

|---|---|---|
| `items.orphan_user` | 38 | `accepted` (известно и принято, но строки лежат) |
| `pokemon.invalid_owner` | 63 | `accepted` |

Итого 102 осиротевшие записи под разбор (38 + 63 + 1) и 230 «висящих» боёв.

Окружение: MySQL 5.5 на порту 3308, подключение `PDO::ATTR_EMULATE_PREPARES => false`
(`src/Database/Connection.php`), миграции идемпотентные, реестр — `schema_migrations`.

## Что сделать (только подготовка)

1. **Разведка, read-only.** Новый `tools/fk_orphan_recon.php` (зона `tools/**` — твоя).
   Для каждой пары-кандидата (таблица.колонка → родитель.колонка) печатает:
   * число осиротевших строк и до 20 примеров (id, значение колонки, дата, если есть);
   * движок каждой таблицы (`information_schema.TABLES.ENGINE`) — **на MySQL 5.5 у
     MyISAM внешних ключей не бывает вообще**, такие таблицы надо назвать прямо;
   * типы колонок с обеих сторон и наличие индекса под FK;
   * есть ли строки со значением `0`/`NULL`, которые трактуются кодом как «нет владельца»
     (это не сироты, а легальный случай — проверь по коду, прежде чем считать их дефектом);
   * по умолчанию инструмент **ничего не меняет**, у него нет режима записи.
   Кандидаты (уточняй по живой схеме, не по памяти): `items_users.user_id`,
   `pok_user.users`, `battles.user_1`, `battles.user_2`, `eggs.user_id`, а также связи,
   которые ты найдёшь сам в боевых, инвентарных и рыночных путях.
2. **План сверки.** Отдельный раздел отчёта: по каждой паре — что делать с сиротами
   (удалить, обнулить, перенести в архивную таблицу, оставить) и какие последствия для
   игрока. Решение принимает владелец; ты предлагаешь варианты с ценой каждого.
3. **Миграция.** Один идемпотентный файл
   `database/migrations/2026_10_13_000001_add_critical_foreign_keys.sql`: добавляет FK
   **только там, где данные уже чистые**; для грязных таблиц — закомментированный блок с
   пометкой «требует сверки» и понятным условием включения. В отчёте — обратные
   операторы (`ALTER TABLE ... DROP FOREIGN KEY ...`) для каждой добавленной связи.
   Миграцию **не применять**: она остаётся `pending`.
4. **Защита от случайного применения.** В отчёт явно: `php tools/beta_backup.php` перед
   любой будущей попыткой применения и прогон `db_integrity_smoke` до/после.
