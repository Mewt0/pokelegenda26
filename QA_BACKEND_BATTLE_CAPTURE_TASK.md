# QA задача: backend/regression по ловле, PvE item-flow и боевой устойчивости

## Цель
Проверить, что исправления ловли покемонов и PvE-ходов работают на реальной БД и через реальные API, без ручной подмены состояния.

## Окружение
- Проект: `D:\OSPanel\domains\pokemonchic.com`
- URL: `http://pokemonchic.com/game`
- MySQL: `127.0.0.1:3308`
- БД берется из `.env`
- PHP: OSPanel PHP 8.1+

## Что обязательно проверить

### 1. Ловля покемона
- Включить PvE и начать бой с диким покемоном, у которого `poimka = 1`.
- Попробовать обычный покебол `item_id=3`.
- При неудачной попытке:
  - количество покеболов уменьшается на 1 в `items_users`;
  - в `battle_log` появляется запись попытки;
  - дикий покемон делает ответный ход;
  - раунд увеличивается только после завершения обмена ходами.
- При успешной попытке:
  - покебол списывается;
  - бой завершается с `result=caught`;
  - новая запись появляется в `pok_user`;
  - для неё создается строка `attac_my_poke`;
  - если активная команда меньше 6, `active=1`;
  - если активная команда заполнена, `active=0`, но покемон виден в меню покемонов как питомник/резерв.

### 2. Разные шары
- Проверить `item_id=25` Premium Ball: доступен в бою, списывается, имеет повышенный шанс.
- Проверить `item_id=90004` Master Ball: доступен в бою, должен ловить с максимальным шансом.
- Проверить, что не-боевой предмет без `battleuse=1` не проходит как шар.

### 3. PvE предметы и смена покемона
- Использовать предмет в PvE:
  - `item_id=217` восстанавливает PP и тратит ход;
  - `item_id=861` лечит HP и тратит ход;
  - `item_id=15` снимает сон и тратит ход.
- После каждого действия дикий покемон должен ответить, если оба живы.
- Смена покемона тоже должна вызывать ответ дикого покемона.

### 4. Завершение боя
- После `ack-end` проверить, что чистятся:
  - `statpokemonbatle`;
  - `battle_dop`;
  - `battle_log`;
  - `bttle_status`;
  - временный `pok_pve`.
- Завершенный бой не должен оставлять статусы, которые могут попасть в следующий бой.

### 5. Тренировки
- Двойной клик по тренировке не должен списывать два предмета при одном результате.
- Проверить, что `pok_user` блокируется через `FOR UPDATE`, а списание предмета и изменение стадии идут в одной транзакции.

## API smoke
- `POST /api/battle/pve/action` с `action=item` для шара.
- `POST /api/battle/pve/action` с `action=item` для предметов `15`, `217`, `861`.
- `POST /api/battle/pve/action` с `action=switch`.
- `POST /api/battle/pve/ack-end`.
- `GET /api/pokemon/moves` после удачной ловли.

## Ожидаемый отчет QA
- Список сценариев `OK/BROKEN`.
- Для каждого BROKEN: payload запроса, JSON-ответ, строки БД до/после.
- Отдельно указать, какой item_id использовался и какой `battle_id`.
